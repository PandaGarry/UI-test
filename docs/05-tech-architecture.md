# 05 · Техническая архитектура

> Цель документа: к моменту старта кода (M1) не должно оставаться открытых вопросов «как это работает». Всё, что здесь описано, реализуемо в этой среде (Node 22, npm, без Docker) и бесплатно тестируемо в Replit.

---

## 1. Требования, из которых всё вытекает

| # | Требование | Следствие для архитектуры |
|---|---|---|
| 1 | 1000+ одновременных игроков в одном мире | Один мир = один процесс (single-writer), асинхронная симуляция, тик 1 Гц, дельты клиенту |
| 2 | Никаких покупок инфраструктуры на старте | Всё запускается локально и в Replit; внешние сервисы — только бесплатные тарифы |
| 3 | Античит «по построению» | Ни одно игровое решение не принимает клиент; все таймеры — серверные |
| 4 | Быстрая итерация баланса | Контент (числа) вынесен в данные, а не в код; рестарт сервера — секунды |
| 5 | Один билд → браузер + Android | PWA + Capacitor из одного фронтенда |
| 6 | Готовность к росту без переписывания | Мир изолирован (shard-by-kingdom); добавление мира = добавление процесса |

**Что мы сознательно не делаем (и почему):** realtime-синхронизацию 20–60 Гц, предсказание клиента, физику, 3D-город. В жанре «city builder + марши» это не нужно: игрок ставит приказ и уходит. Это экономит 60–70% сложности и делает 1000 CCU рутиной.

## 2. Стек (конкретный выбор)

| Слой | Выбор | Почему именно так | Альтернативы и почему нет |
|---|---|---|---|
| Сервер | **Node 22 + TypeScript (strict)**, ESM | Работает здесь и в Replit без установок; детерминизм и скорость итераций важнее максимума производительности (нам нужно 0,5 vCPU на мир, не 8) | Go (быстрее, но нет в среде и нет экосистемы) · C# (тяжелее деплой) |
| Транспорт | **WebSocket** + бинарный **Protobuf** (`ts-proto`) | Дешёвый трафик (мобилка!), строгая типизация, версии протокола | JSON (в 2–3 раза больше трафика) · gRPC-web (лишний слой) |
| Мировой цикл | Свой планировщик: **min-heap задач + тик 1 Гц** | Именно он даёт «1000 игроков на мир» дёшево | Cron/Redis-очереди (лишняя инфраструктура) |
| БД (dev) | **SQLite (better-sqlite3)** | Ноль зависимостей, файл, работает где угодно; скорость разработки | Postgres локально (без Docker недоступен) |
| БД (prod) | **Postgres (Neon/Supabase, free tier)** | Бесплатно, надёжно, знакомо | CockroachDB/Mongo — оверкилл |
| ORM/миграции | **Drizzle** | Один код миграций для SQLite и Postgres, типы из схемы | Prisma (тяжелее, хуже с SQLite в рантайме) |
| Клиент | **React 19 + Vite + Zustand + PixiJS 8** | React — интерфейсы, Pixi — карта; разделение «UI vs игровое поле» | Unity/Cocos (не проверяемы здесь) · Phaser (слабее для больших карт) |
| Мобильный рантайм | **PWA (первым делом) → Capacitor (Android)** | Один код; PWA даёт установку на домашний экран сразу | Native/Unity (дорого) · Cordova (устарел) |
| Стили | **CSS Modules + дизайн-токены** (переменные темы Явь/Навь) | Без сборщиковых зависимостей и без Tailwind-классовой каши | Tailwind (можно, но дизайн-токены важнее) |
| Тесты | **Vitest** + property-тесты | Быстро, ESM «из коробки» | Jest (медленнее, ESM-боль) |
| Линт/формат | **Biome** | Один инструмент, один конфиг, без ESLint-плагинового ада | ESLint+Prettier (два конфига, больше шума) |
| Логи/метрики | **pino** + `prom-client` (опционально) + админ-дашборд | Наблюдаемость нужна с первого дня | Sentry/Grafana — позже, на реальном хосте |
| Наблюдаемость мира | **`tools/admin`** — веб-дашборд: тик, очередь, CCU, кадр карты | Это же — «превью» для тебя и инструмент отладки | — |
| CI | **GitHub Actions** | Уже есть GitHub; бесплатно | — |
| Контейнеры | **Docker — не нужен на старте** | Недоступен в среде, а на free-хостингах обычно не обязателен | — |

## 3. Структура монорепозитория (npm workspaces)

```
UI-test/
  package.json                 # workspaces root, скрипты: dev, build, test, load
  packages/
    protocol/                  # .proto → ts-типы, коды ошибок, версии, zod-валидация команд
    content/                   # ВСЕ игровые данные: здания, войска, герои, науки, события, тексты
      buildings.ts  units.ts  heroes.ts  research.ts  events.ts  story/prologue.ts ...
      names/                   # генераторы имён для Мороков и городов
    rules/                     # чистая детерминированная логика: формулы боя, производство, тайминги
                               # (используется и сервером, и клиентом для «предпросмотра» цифр)
    sim-core/                  # планировщик, мир, тайлы, марши, сущности (без сети и без БД)
    telemetry/                 # схема событий аналитики (единый словарь для клиента и сервера)
  apps/
    server/                    # вход, WS-шлюз, сессии, команды, БД, шардинг миров
    client/                    # React + Pixi: острог, карта, экраны, .proto-клиент
  tools/
    admin/                     # дашборд мира (метрики + карта + очередь тика)
    botfleet/                  # нагрузочные боты (они же — «Мороки» в проде, общий код ИИ)
    econ-sim/                  # прогон экономики на 90 игровых дней
  docs/                        # этот пакет
```

**Правило зависимостей (важно и проверяется линтом):**
`protocol → (ничего)` · `content → protocol?нет` · `rules → content, protocol` · `sim-core → rules, content` · `apps/server → sim-core` · `apps/client → rules(только чтение!), protocol` .
Клиент **никогда** не импортирует `sim-core` — иначе соблазн «посчитать бой локально» и получить чит.

## 4. Топология

```
        ┌──────────────── Клиент (PWA / APK, WebGL) ────────────────┐
        │  React UI  │  PixiJS карта  │  локальные таймеры по серверному времени
        └───────┬───────────────────────────────┬──────────────────┘
                │ WebSocket (binary protobuf)   │ HTTPS (статика)
                ▼                               ▼
        ┌───────────────────────────┐   ┌──────────────────┐
        │  Gateway (WS)             │   │ CDN / статика    │
        │  сессии, auth, rate-limit │   │ (Cloudflare Pages│
        │  маршрутизация в мир      │   │  / Vercel free)  │
        └───────────┬───────────────┘   └──────────────────┘
                    │ внутренний канал (in-proc; позже Redis/NATS)
                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │  Мир #N  (single writer, 1 процесс = 1 королевство)      │
        │  ┌──────────────┐  ┌──────────────┐  ┌────────────────┐ │
        │  │ Тик 1 Гц     │→ │ Планировщик  │→ │ Команды игроков│ │
        │  │ день/ночь,Мор│  │ min-heap     │  │ (валидация+WAL)│ │
        │  └──────────────┘  └──────────────┘  └────────────────┘ │
        │  состояние: тайлы, города, марши, Роды, лагеря, боты     │
        └───────────┬──────────────────────────────┬───────────────┘
                    │ снапшоты/дельты              │ журнал событий
                    ▼                              ▼
        ┌───────────────────────┐        ┌──────────────────────────┐
        │ Postgres (Neon/Supabase) │      │ Бэкапы/реплеи (S3-like,  │
        │ аккаунты, прогресс, лог  │      │ опционально, позже)      │
        └───────────────────────┘        └──────────────────────────┘
```

**Разделение «шлюз vs мир»:** на старте это один процесс (шлюз и мир в одном), но с самого начала в коде — по интерфейсу, чтобы вынести шлюз позже без переписывания. Это принцип «граница есть, процесса пока нет».

## 5. Модель симуляции (главное)

### 5.1 Три источника изменений
1. **Команды игроков** (построить, отправить марш, лечить…) — валидируются, кладутся в очередь мира, применяются в **детерминированном порядке** (серверный номер, а не «кто первый»).
2. **Планировщик** (min-heap по времени срабатывания): завершение постройки, приход марша, спавн лагеря, смена фазы суток, тик Мора.
3. **Мировой тик 1 Гц**: догоняет «протухшее» (ленивое разрешение), обновляет агрегаты (рейтинги, обзор, погода), раздаёт дельты подписчикам.

### 5.2 Почему это держит 1000+ игроков
- Игрок ставит приказ и уходит. В момент запроса сервер делает **O(1)** работы + 1 запись в heap.
- Ресурсы не «капают» в БД каждую секунду: производство считается **лениво** — `amount += rate * (now − lastSettled)` при любом обращении (заходе, сборе, атаке). Один игрок = одно «догоняющее» вычисление на визит.
- Бой считается в момент прибытия марша, а не «покадрово»: один раз, в одном процессе, без гонок.
- Карта хранится как **seed + дельты**: 512×512 тайлов генерируются детерминированно из зерна мира (математика воспроизводима), а в БД — только изменения (занятые тайлы, истощённые узлы, постройки). Это экономит БД и память.
- Пуш клиенту — только по подпискам (свой город, область карты, Род, чат). Не «всем всё», а «каждому его».

### 5.3 Детерминизм и честность
- Порядок применения команд внутри одного тика фиксирован (сортировка по `serverSeq`).
- `cmdId` (UUID от клиента) → идемпотентность: повтор команды (потеря сети) не даёт второго эффекта.
- Журнал: `command_log` (что просили) + `event_journal` (что произошло) → реплей мира из снапшота для разбора жалоб и античита.
- Хеш состояния (`stateHash`) раз в 60 секунд в лог: если мир «поехал», это видно сразу.

### 5.4 Сохранение состояния
- Снапшот в БД каждые 60 секунд + при завершении важных транзакций (покупки, бой, сезонные события).
- Перед ответом на действие, влияющее на ценности (покупка Гривен, бой, обмен) — «жёсткая» запись (не откладываем).
- Восстановление мира из снапшота + журнал с последнего снапшота.

## 6. Протокол

### 6.1 Форматы
- Транспорт: WebSocket, бинарные кадры Protobuf (не JSON — мобильный трафик).
- Обёртка кадра: `[1 байт версия][1 байт тип][payload]`.
- Версионирование: `protocolVersion` в рукопожатии; сервер поддерживает N−1 совместимость, клиент обязан обновиться при разрыве (PWA/APK умеют).

### 6.2 Команды клиент → сервер (набор M1–M2)
```
Auth{deviceId, token?}                      → AuthOk{playerId, serverTime, clockOffset}
JoinWorld{worldId|auto}                     → WorldSnapshot{meta, city, viewport, kin}
SubscribeViewport{x,y,w,h, zoom}            → ViewportPatch{...}
UnsubscribeViewport{token}
Cmd{cmdId, type, payload}                   → Ack{cmdId, ok, code?}   # асинхронный результат — событием
```
Типы `Cmd` (M1–M2): `BuildStart`, `BuildCancel`, `BuildSpeedup`, `TrainStart`, `ResearchStart`, `HealWounded`, `MarchCreate`, `MarchRecall`, `Scout`, `GatherStart`, `RallyJoin`, `KinCreate/Join/Leave/Help`, `ChatSend`, `MarkSet`, `WatchpostBuild`, `ThreadCreate`, `PurchaseStart` (серверная проверка чека), `ClaimDaily`, `RitualComplete`.

### 6.3 Пуш сервер → клиент
| Сообщение | Кому | Частота |
|---|---|---|
| `CityPatch` | владельцу | при изменениях (батч 4 раза/с максимум) |
| `ViewportPatch` (дельты тайлов/маршей) | подписчикам области | при изменениях, не чаще 4 Гц |
| `MarchState` | владельцу | раз в 5 с + при событиях |
| `BattleReport` | участникам | по факту боя |
| `KinPatch`, `ChatPush` | членам Рода | при изменениях |
| `LeaderboardPatch` | топ-подписчикам | раз в 30 с |
| `WorldMeta` | всем | смена фазы суток/погоды/события |
| `Notify` | адресно | по факту |

### 6.4 Время
- Все таймеры считает сервер, клиент получает абсолютные `startedAt`/`endsAt` (UTC мс) и рисует отсчёт, зная `clockOffset` (считается по пингу при входе, обновляется каждые 5 минут).
- Клиент **не отправляет** «прошло столько-то» — только намерения («ускорить», «применить»).

## 8. Масштаб: расчёты и оценки

**На один мир (1000 активных CCU, 512×512):**

| Параметр | Оценка | Комментарий |
|---|---|---|
| Состояние мира в RAM | 60–150 МБ | тайлы 4 МБ + города ~1000×20 КБ + марши + боты |
| Соединения | 1000 WS × ~60 КБ | ~60 МБ на процесс (буферы, сессии) |
| Сообщения | 1 500–4 000 msg/s | 0,3–1 команда/с на игрока + пуш по изменениям |
| CPU | 0,3–0,7 ядра | тик 1 Гц + обработка команд + бои по факту |
| Трафик | 10–40 МБ/ч на 1000 игроков | бинарные дельты по области обзора |
| Хранилище | ~1–3 ГБ/сезон на мир | с агрегацией отчётов и дельтами карты |

**Вывод:** один мир — это небольшой VPS (2 vCPU / 4 ГБ) с большим запасом; 10 миров = 10 таких процессов (можно по 2–3 на сервер). Оценка стоимости для продакшн-демо: **от ~$5–20/мес** за один мир с запасом (free-tier хватает для тестов с друзьями, но не для публичного запуска круглосуточно).

**Шардинг:** `worldId` определяет процесс. Роутинг — по игроку (его аккаунт знает свой мир). Кросс-мировых механик на старте нет (это большое упрощение и защита от «сложности на пустом месте»).

## 9. Авторитарность и античит

| Угроза | Защита |
|---|---|
| Подмена клиента (модифицированный APK) | Клиент не влияет ни на что: сервер проверяет каждый приказ против своего состояния |
| Повтор команд / «дребезг» сети | `cmdId` + idempotency-таблица |
| Спам запросами (DoS игрового слоя) | Лимиты по типам (напр.: сбор ≤ 1/мин, помощь ≤ 20/час, чат ≤ 1/3 с, команд ≤ 10/с), бан за аномалии |
| «Ускорить» без оплаты | Все тайминги серверные; ускорение = отдельная сущность, списывается транзакционно |
| Фальшивые покупки | Проверка чека на стороне магазина (Google Play/ЮKassa webhook) → выдача только после подтверждения |
| Договорные бои («фарм убийств») | Анти-абуз: награды за убийства только между «не связанными» игроками (не из своего Рода, не с одного IP/устройства, не чаще N раз по одному сопернику) |
| Мульти-аккаунты | deviceId + поведенческие признаки; мягкие ограничения (не бан, а «нет наград за PvP между связанными») |
| Внутренний абьюз (сам админ) | Все админские действия — через журнал, с причиной, видимым в `event_journal` |

## 10. Нагрузочный тест и Мороки (одна кодовая база)

`tools/botfleet` — процесс(ы), которые держат **настоящие WebSocket-соединения** и играют по расписанию:

- профили: `casual` (3 захода/день), `active` (6), `whale` (10, покупки-моки), `griefer` (постоянные атаки);
- поведение: войти → собрать → построить → обучить → отправить марши → собрать → выйти, с реалистичными паузами;
- масштаб прогонов: 50 (smoke), 300 (CI nightly), **1000+ (целевой прогон)**, 2000 (стресс);
- метрики прогона: RTT p50/p95/p99, «просрочки» тика (`tick lag`), msg/s, RAM/CPU процесса мира, ошибки команд, средний размер дельты, время реакций на 1000 одновременных команд;
- критерий приёмки M6: **1000 ботов, тик не просрочен более чем на 50 мс в 99% случаев, p95 RTT команды < 150 мс, процесс мира < 1,5 vCPU и < 1,5 ГБ RAM**, ни одного потерянного состояния при рестарте.

Это же приложение конвертируется в «Мороков»: тот же ИИ, только тиры поведения (см. ГДД §14). Отдельного «бота-наполнителя» писать не нужно.

## 11. Клиент

### 11.1 Карта (PixiJS)
- Тайловая отрисовка с **culling** (рисуем только видимое окно, ~30×20 тайлов) и LOD (три уровня детализации: иконка/упрощённый/полный).
- Мгновенный отклик: карта двигается сразу, данные приходят дельтой (не ждём сервер).
- Нити оберега — кривые линии с шейдером «света» (одна текстура + аддитивное смешивание).
- Слой маршей — отдельный контейнер (перерисовывается чаще остального).
- Игрок в темноте/тумане — просто затемняющая маска: дёшево и атмосферно.

### 11.2 Состояние и данные
- `Zustand` хранит: город, войска, очереди, Роды, отчёты, настройки UI. Кэш карты — отдельно, с LRU.
- Ассеты: ленивая подгрузка по экранам; базовый пакет < 12 МБ; звук — по требованию.
- Все тайминги — производные от серверного времени (см. §6.4); после возврата из фона (мобилка!) идёт «догон» и запрос снапшота, а не доверие локальным часам.

### 11.3 PWA и Android
- PWA: манифест, оффлайн-шеллинг (только оболочка, не игровые данные), версия ассетов, кнопка «на домашний экран» после первого боя.
- Capacitor: тот же билд → Android; добавляем нативные вещи, которые нельзя в вебе: пуш-уведомления (FCM), вибро, покупки (Google Play Billing), позже — иконка/сплэш.
- Веб — единственный вариант, где мы можем проверять всё здесь; APK собираем на твоей машине (или в CI, если добавим сборку Android позже).

## 12. DevX, команды, CI

**Команды (появятся в M1):**
```
npm run dev            # сервер + клиент с горячей перезагрузкой (один порт для превью)
npm run dev:world      # создать тестовый мир 128×128 и населить 300 Мороками
npm run load:1000      # нагрузочный прогон 1000 ботов + отчёт в консоль и в admin
npm run econ:sim       # прогон экономики на 90 дней, отчёт по кривой силы и стокам
npm run test           # vitest (rules, sim-core, server)
npm run typecheck      # tsc --noEmit по всем пакетам
npm run lint           # biome
npm run db:migrate     # drizzle
npm run admin          # дашборд мира (отдельный порт)
```
**CI (GitHub Actions, бесплатно):**
- PR: lint → typecheck → test → build → smoke-нагрузка 50 ботов (2 минуты).
- Nightly: 300 ботов 30 минут + econ-sim 90 дней, отчёт как артефакт.
- Тег/релиз: сборка клиента + публикация статики (Pages/Cloudflare), миграции БД — по подтверждению.

## 13. Деплой без VDS (что реально бесплатно)

| Что | Где (free) | Ограничения, которые надо знать |
|---|---|---|
| Клиент | Cloudflare Pages / GitHub Pages / Netlify | статика; домен бесплатный поддомен |
| Сервер (демо на 5–30 человек) | Replit (есть всегда-включённый режим в платных тарифах; бесплатный спит), Render free (засыпает через 15 мин простоя — для WS плохо) | для «поиграть с друзьями» — ок, для публичного запуска — нет |
| БД | Neon / Supabase free | лимиты по размеру и «холодному старту» |
| Файлы/бэкапы | Backblaze B2 / R2 free tier | мелочи |
| Уведомления | FCM (бесплатно) | только в APK/PWA с поддержкой |
| Реальный продакшн-демо | $5–20/мес VPS или Fly.io/Railway | **это первый момент, когда появляются деньги** — и то не на старте |

Честная формулировка для тебя: **ноль рублей до момента, когда мы хотим, чтобы игра работала круглосуточно для незнакомых людей.** Для тестов и разработки — Replit/эта среда, бесплатно.

## 14. Безопасность и данные

- Минимум персональных данных: `deviceId` + опционально email/соцвход. Никаких «дата рождения, пол, телефон» на старте.
- Пароли не храним в открытом виде (Argon2id) — если вообще делаем парольный вход (сначала лучше device-токен + привязка почты по желанию).
- Все покупки — через официальные биллинги; мы не касаемся платёжных данных.
- ФЗ-152: при запуске в РФ — данные российских игроков в российском ЦОД (иначе только вне РФ). Решение: готовим «миграцию локации» как план, а не как сюрприз.
- Дети: возрастной рейтинг 12+, никакой рекламной таргетированной обработки, никаких лутбоксов без раскрытия шансов.
- Логи: без персональных данных в тексте, ретеншен ограничен (30–90 дней).

## 15. Тестирование (что именно проверяем)

| Тип | Что проверяет | Инструмент |
|---|---|---|
| Unit | формулы боя, производство, тайминги, гейты требований | Vitest |
| Property | инварианты: ресурсы не отрицательны; сумма ресурсов = источники − стоки; нет «бесплатных» ускорений | fast-check |
| Determinism | одинаковые seed + команды → одинаковый `stateHash` | Vitest + хеш |
| Replay | из журнала воспроизвести любой бой и получить тот же результат | `event_journal` |
| Command fuzz | команды с мусорными параметрами не ломают мир | fuzz-раннер |
| Load | 1000 ботов, метрики §10 | botfleet |
| Economy | 90 дней, 4 архетипа, кривая силы и тайминги | econ-sim |
| Client smoke | все экраны открываются, нет «пустых» состояний, кнопки не «мертвы» | Playwright (позже) |

## 16. Технические риски и решения

| Риск | Решение |
|---|---|
| SQLite в dev ≠ Postgres в prod (разное поведение) | Drizzle + тесты на обоих диалектах в CI |
| Утечка состояния мира при рестарте | снапшот + журнал + идемпотентный реплей; процедура проверена тестом «убить процесс на середине боя» |
| Растущая цена боя (ралли 8×1000 отрядов) | расчёт на сервере в одном месте с лимитом раундов и O(классы) на раунд, а не O(юниты); профилирование в CI |
| Размер карты и «1 млн тайлов» в памяти | seed + дельты; снапшоты карты не храним |
| Клиент на слабом Android | бюджет производительности из §11+ГДД §18, проверка на «медленном» профиле в Chrome |
| Куча экранов = долгая разработка UI | дизайн-система из 12 компонентов, «унылые» экраны генерируются из данных |
| Рост числа миров «руками» | `tools/admin` + скрипт `world:create`, позже — автосоздание по расписанию |
