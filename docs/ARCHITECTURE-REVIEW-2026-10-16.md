# Сверка архитектуры клиента: замер и предложение (2026-10-16)

## Что это значит
1. **Ядро не отделено.** `game/` импортирует сеть, ввод, карту. Ядро должно быть чистым: без DOM, без сети.
2. **DOM в ядре:** `window`/`document` в трёх файлах `game/` (`Game.ts`, `MapActionHandler.ts`, `MapNavigationHandler.ts`).
3. **Циклы:** `game ↔ map`, `game ↔ network`, `util ↔ (game, renderer, ui)`. Из-за них любая правка тянет половину кода.
4. **`util` — свалка** (29 файлов, зависит от всего). Это главный источник «правишь мелочь — трогаешь половину».
5. **Сервер использует симуляцию** через относительные импорты из `client/src/game` (`server/src/game/Game.ts`, `runner/Runner.ts`). Значит ядро — общая библиотека, и её границу надо выделить явно.
6. **Тесты:** `client/test/` покрывает только небольшую часть (game, util, render). Без тестов рефакторинг рискован.

## Предложение: не переписывать с нуля, а выделять по шагам
Целевая структура (npm workspaces, один репозиторий):
- `packages/core` — симуляция, правила, карта (данные), детерминированные утилиты. Без DOM, сети, рендера. Используется клиентом и сервером.
- `packages/mapgen` — генератор карт (G/V/T/R из спецификации). Работает в Node и в браузере, не зависит от клиента.
- `packages/client` — рендер, ввод, UI, сетевой клиент. Зависит от core.
- `packages/server` — сеть, матчи. Зависит от core.

Шаги (каждый шаг проверяется тестами и побайтной регрессией симуляции):
1. Правила границ: lint-правило (dependency-cruiser или eslint boundaries) с запретом `core → (ui|renderer|network|event)`. Пока только предупреждения, список нарушений в отчёте.
2. Разрыв циклов: `util` разбить по смыслу (чистые утилиты в core, DOM-утилиты в client), `game ↔ map` и `game ↔ network` через интерфейсы.
3. Вынос `core` в `packages/core` и workspaces. Сервер импортирует пакет вместо относительных путей.
4. Регрессия: одинаковый сид + одинаковый набор команд → одинаковое состояние (это же проверка детерминизма из этапа 2).
5. Только после этого — `mapgen` и визуальные слои.

## Сравнение вариантов
| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Полный перенос сейчас | Чисто сразу | Большой риск поломки, долго, нет промежуточных проверок |
| B. Пошагово (рекомендую) | Каждый шаг проверяем, работа над картой не стоит | Дольше в переходный период, пара промежуточных костылей |
| C. Не трогать, только новый код отдельно | Быстро | Долг растёт, мелкие правки остаются дорогими |

Рекомендация: вариант B. Сначала границы и разрыв циклов (шаги 1–2) — они дают основной выигрыш. Перенос в workspaces (шаг 3) — после зелёных тестов.
