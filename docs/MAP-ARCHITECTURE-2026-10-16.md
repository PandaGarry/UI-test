## 1. Как устроено у эталона

### 1.1 Фундамент (игровой слой) — один байт на клетку
Вход: PNG, рельеф кодируется **синим каналом**. Выход: `map.bin` (1x), `map4x.bin`, `map16x.bin` + `manifest.json`.

| Бит | Смысл |
|---|---|
| 7 | суша (1) / вода (0) |
| 6 | берег (клетка на границе суша–вода) |
| 5 | океан (вода, связанная с краем карты) |
| 0–4 | величина: для суши — высота 0–31; для воды — расстояние до суши (делится на 2) |

Особые значения: `0b10011111` = **непроходимая** клетка (суша + величина 31, не занята, не атакуется, ядерные траектории не пересекает). Чёрный пиксель (#000) — непроходимая. Чистый синий 106 — вода.

Правила генерации (из `map_generator.go`):
- суша: высота = `(blue − 140)/2`, зажата в 0…30; вода: величина = BFS-расстояние до суши;
- удаление мелких тел суши **< 30 клеток**, озёр (водных тел внутри суши) **< 200 клеток**;
- вода, соседствующая с непроходимым, получает максимальную глубину (без градиента);
- уменьшение (4x, 16x) по **приоритету воды**: если в блоке 2×2 есть вода, клетка — вода. Это сохраняет узкие реки для поиска пути;
- размеры кратны 4; рекомендуемая площадь 2–3 млн клеток, суши 1–2 млн, предел 3 млн.

### 1.2 Визуальные слои — отдельные файлы, переключаются игроком
- В `info.json` массив `layers`: `{id, placement: "land"|"water", nukeable}`. Картинка `<id>.png` того же размера, что `image.png`.
- Генератор пишет WebP (качество 90) полного размера и 4x. Lossy допустим, потому что **какие клетки покрыты, решают байты фундамента, а не картинка**.
- Слой рисуется между рельефом и территориями. Игрок выключает его и меняет прозрачность в графических настройках (`mapLayerVisibility`, `mapLayerAlpha`). Значения по умолчанию задаются в манифесте.
- Единственное игровое свойство слоя — `nukeable`: при ядерном ударе слой постоянно уничтожается в радиусе. Сейчас у нас ядерного оружия нет.

### 1.3 Цвет на клиенте
Цвет клетки считается **на клиенте из байта** (`encodeTerrainTile`): суша/берег/оттенок по величине (равнина, холм, гора, песок), вода по глубине (`oceanColor`). Палитра лежит в `render-settings.json` и переопределяется темой. Фон непроходимых = цвет фона. Файл карты не содержит цветов.

## 2. Что у нас (и что не так)

| № | Наблюдение | Почему это проблема |
|---|---|---|
| A1 | Карта кодируется индексом типа (`Uint16`) и таблицей типов. В таблице смешаны игровые (`conquerable`, `navigable`, `expansionCost/Time`) и визуальные (`colorBase`, `colorVariant`) поля. | Визуальные данные попадают в фундамент. Меняя картинку, мы меняем файл игры. |
| A2 | `colorBase`/`colorVariant` записываются в бинарник и **не читаются** ни одним потребителем (проверено grep: только кодек). | Мёртвые байты в каждой карте. |
| A3 | Тип клетки берётся из цвета PNG (ближайшая палитра). | Антиалиасинг и любая визуальная правка по цвету меняют геймплей. Так нельзя при текстурах и реках. |
| A4 | Нет береговой линии, океана, величины воды (расстояния). | Нет основы для темпа по воде, для рек (сток к морю) и для рельефа с реальной высотой. |
| A5 | Рельеф задан квантилями внутри суши (мой пилот), а не высотой. | Горные хребты и реки не получаются осмысленно: «гора» — просто верхние 28% суши. |
| A6 | Палитра и тема определяют цвет на клиенте (`MapRenderer`, `distanceMap`), а не файл. | Это правильно и совпадает с эталоном: сохраняем. |
| A7 | Нет миниатюр 4x/16x. | Нужны и для обзора, и для поиска пути на лодках (предупреждение M6). |

## 3. Предлагаемая архитектура

### 3.1 Принцип
- **Фундамент F** — единственный источник правды для симуляции. Детерминированный, компактный, проверяемый тестами. Генерируется офлайн один раз, хранится файлом. Клиент и сервер читают один файл.
- **Визуальные слои** — всё, что только отрисовывается. Никогда не меняют F. Каждый слой может быть выключен игроком, и игра остаётся одинаковой.
- **Правило переноса** (владелец должен согласовать): если визуальный слой начинает влиять на атаку, он переходит в F. Такой переход — отдельное решение с записью в `PARITY.md`.

### 3.2 Формат фундамента F (версия 1)
Один байт на клетку, как у эталона (проверено и совместимо по смыслу):

```
bit 7 land | bit 6 shore | bit 5 ocean | bits 0–4 magnitude (0–31)
непроходимо: 0b10011111
```

- Тип клетки для игры **выводится** из байта: `Water` (величина = глубина), `Plains` (<10), `Hills` (10–19), `Mountains` (≥20). Пороги и стоимость захвата (`expansionCost`/`Time`) — в одной таблице в `BalanceConfig`, **не в файле карты**.
- Файл карты больше не содержит `colorBase`/`colorVariant`. Таблица типов в файле сводится к версии и ссылке на баланс.
- Совместимость: версия в заголовке, как у `MapCodec` (`CURRENT_VERSION`). Новый формат — новая версия, старый читается.
- Миниатюры 4x и 16x вычисляются тем же правилом приоритета воды, что и у эталона. Хранятся в том же файле или отдельно (решение в шаге 2 плана).

### 3.3 Визуальные слои V / T / R
Таблица по предложению из `MAP-GENERATOR-SPEC` раздел 6, сверена с эталоном:

| Слой | Что | Файл | Выключается игроком | Влияет на игру |
|---|---|---|---|---|
| **V** — базовый | цвет по величине и берегу, оттенки, затенение по высоте, пена у берега | вычисляется на клиенте из F и темы | нет (всегда) | нет |
| **T** — текстуры | атлас для равнин, холмов, гор, воды | WebP-атлас, качество выбирает игрок (выкл / низкое / высокое) | да | нет |
| **R** — реки и озёра (вид) | ленты рек, озёра по данным F | WebP-слой `rivers` с `placement: water` | да | нет (пока) |
| **B** — биомы | лес, пустыня, тундра по высоте и влажности (шум) | WebP-слой `biomes` | да | нет |

- Каждый слой описан в `info.json`-подобном манифесте: `id`, `placement`, `default_visible`, `default_alpha`, `nukeable` (зарезервировано, `false`).
- Настройки качества управляют **только** T, R, B. F не зависит от настроек. Это прямое требование владельца («фундамент прочный и одинаковый»).
- Реки строятся по F: сток от высоких клеток к морю по убыванию величины. Это вид, поэтому не влияет на атаку.

### 3.4 Производительность (бюджеты)
- Фундамент 2000×1000: 2 МБ несжатых байт. Ожидаемо 100–300 КБ после сжатия кодеком. Измерить на пилоте.
- Миниатюры 4x/16x: проверка на слабом устройстве, FPS и память до принятия.
- Визуальные слои: WebP на сервере/CDN, на клиенте декодируются один раз. Выключенный слой не грузится.
- Бюджеты фиксируем до реализации (в `VISION.md`, раздел производительности): время загрузки карты, память, FPS на мобильном профиле.

### 3.5 Что меняется в коде (оценка, без реализации)
1. `packages/core/src/map/codec`: версия 1, фундамент F, без визуальных полей (тесты на round-trip и на старую версию).
2. `GameMap`: величина и флаги берега/океана вместо готовых типов; выводимые типы по порогам.
3. `client/scripts/generate-local-maps.ts`: вместо палитры PNG — чтение F из генератора.
4. Генератор (`client/scripts/maps/`): высота → F → миниатюры → визуальные слои. Текущий пилот переделать по этой схеме.
5. Клиент: слой V из F + тема; слои T/R/B через манифест и `MapLayerController`-подобный механизм; настройки качества в «Графика» (этап 2b.5).
6. Тесты: инварианты (суша в допуске, связность, острова ≥ порога, вода по BFS), детерминизм (побайтно), соответствие F ↔ визуалам, выключение слоя не меняет результат симуляции (регрессия `determinism-check`).

## 6. Что уже известно про пилот (для следующего шага)
- Пилот по архитектуре **переписывается**: сначала высота, затем F, затем визуал. Текущий пилот (квантили палитры) для фундамента не годится (A5).
- Проверка по нескольким сидам обязательна (пилот: тела 19–57, крупнейший материк 31–62% на разных сидах).
- Визуальная сверка с эталоном обязательна до цифр.
